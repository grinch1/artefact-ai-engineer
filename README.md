# Empório da Música — AI customer service agent

A Python prototype for the Artefact AI Engineer case. A language model answers customers in Brazilian Portuguese using four read-only tools for instruments, orders, structured policies, and installment calculations. There are no fixed customer-facing answers: every chat response is generated by the selected model. Before each answer, the application retrieves relevant sections from the versioned `policy.json`, which was reviewed against the supplied private PDF.

## Run locally

The case ZIP supplies six CSVs and an internal policy PDF. Keep them outside the repository. `policy.json` contains a customer-facing summary of the operational rules, with section/page references and typed facts; it omits conflicting contact details and internal procedures. At startup, the application checks its source hash against the PDF when the PDF is present. Set `DATA_DIR` to the extracted `data` directory, which must contain the `products`, `categories`, `promotions`, `orders`, and `customers` CSVs. The `order_items` CSV is outside the current tool scope.

Install dependencies:

```bash
git clone https://github.com/grinch1/artefact-ai-engineer.git
cd artefact-ai-engineer
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export DATA_DIR=/absolute/path/to/case/data
```

Install [Ollama](https://ollama.com/download) and download the [gpt-oss 20B model](https://ollama.com/library/gpt-oss). Ensure the Ollama service is running, then:

```bash
ollama pull gpt-oss:20b
export AGENT_MODE=ollama
export OLLAMA_BASE_URL=http://127.0.0.1:11434/v1
export OLLAMA_MODEL=gpt-oss:20b
uvicorn api:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000/` for the web chat or `http://127.0.0.1:8000/docs` for the API. The interface needs the server; opening `web/index.html` as a `file://` page does not start a chat. For a CLI chat, use `python agent.py --data-dir "$DATA_DIR" --ollama`.

## Run on the private Mainframe

The recorded evaluation used two RTX 3090 GPUs on a private Mainframe. With authorized SSH access, create a local tunnel to its Ollama service in one terminal:

```bash
ssh -N -L 127.0.0.1:11435:127.0.0.1:11434 mainframe
```

In another terminal, use the setup above with this endpoint:

```bash
export AGENT_MODE=ollama
export OLLAMA_BASE_URL=http://127.0.0.1:11435/v1
export OLLAMA_MODEL=gpt-oss:20b
uvicorn api:app --host 127.0.0.1 --port 8000
```

The tunnel is local only and does not publish Ollama. The separate `ager-agents-platform` repository documents a private OpenAI-compatible gateway for its own clients; this isolated experiment uses SSH forwarding rather than modifying that platform or claiming gateway integration.

## Hosted model option

Set `AGENT_MODE=openai` and `OPENAI_API_KEY` to use a hosted model through the Responses API. `OPENAI_MODEL` selects the model and currently defaults to `gpt-5.4-mini`; this path has not yet had an end-to-end model evaluation. API billing is separate from a ChatGPT Plus subscription. Do not place keys in the repository or Docker image. The CLI uses hosted mode when `--ollama` is omitted and an API key is configured. `--demo` only prints retrieval results; it does not produce chat responses.

Docker builds the same API with private data mounted read-only. A container needs network access to the chosen model endpoint; the local SSH tunnel address inside a container is not the host's loopback address. This runtime networking has not been verified locally.

```bash
docker build -t emporio-agent .
docker run --rm -p 8000:8000 -e AGENT_MODE=openai -e OPENAI_API_KEY \
  -v "$DATA_DIR:/data:ro" emporio-agent
```

## Architecture and decisions

`POST /chat` keeps a short conversation in memory. The small HTML/CSS/JavaScript interface calls the same endpoint. The model may call only `search_products`, `get_order`, `get_policy`, and `check_installment`; it cannot generate arbitrary SQL or change source files. CSVs are loaded once into typed in-memory SQLite tables. This keeps exact product, promotion, stock and order queries relational; a vector database would introduce approximate matching where exact amounts and identity checks are required. Only active promotions are applied. `search_products` returns current and original prices, promotion percentage, PIX price, and stock from the snapshot. `get_order` returns a status only when the order number and purchase email match; it omits customer contact details.

The tool allowlist is split by domain in `agent_tools/`: `catalog.py` defines exact catalog lookup, `orders.py` defines verified order lookup, and `policy.py` defines policy retrieval and installment checking. `agent_tools/__init__.py` owns dispatch and rejects unknown operations. Four focused tools keep the model's choices understandable and testable.

The private PDF was reviewed into `policy.json`: customer-facing summaries, typed facts, Portuguese retrieval keywords, and original page/section references. The PDF's hash is recorded to catch a source mismatch. Before **every** model answer, the application retrieves up to three relevant policy objects. The model may make additional tool calls. The backend calculates an explicitly requested installment from the structured bands and supplies the verified result; the model writes the answer. This separation keeps arithmetic and business rules auditable without replacing chat responses with templates. Section search is deterministic and has explicit paraphrase hints; it can still miss unfamiliar wording.

Currency calculations use decimal arithmetic and conventional half-up rounding to cents, an explicit assumption because the manual does not specify a rounding method.

The policy prefetch is a grounding step, not a guarantee of compliance. Local trials compared Qwen 2.5 7B, Qwen3 14B and `gpt-oss:20b` on the same Mainframe. `gpt-oss:20b` is the selected local model, with Ollama reasoning set to `medium`; Qwen3 remains selectable through `OLLAMA_MODEL`. The first keyword search missed paraphrases such as “Onde fica a loja?” and overranked irrelevant sections; the structured index and retrieval tests now cover those cases. An earlier model run rejected 10x correctly but suggested an invalid alternative, motivating backend calculation and an answer check. The agent also retries known unsupported claims about conflicting contact details and unavailable freight quotes. These guards target observed failures; no finite test set can guarantee every model response. A paid hosted model remains a later option. No production readiness is claimed.

The PDF has inconsistent phone and email details across sections, so `policy.json` omits them and the answer gate rejects them. The CSVs are static snapshots, not live inventory or carrier tracking. Sessions reset on restart. This prototype has no authentication or rate limiting and should not be exposed publicly. Matching a purchase email is a demonstration guard, not strong identity verification. For production, replace the CSV import with authenticated inventory/order APIs or a maintained relational database, add real customer verification, rate limits, policy approval/versioning, telemetry, and human handoff. A vector index would be justified only if measured semantic search needs grow beyond this small policy set; it would never be the source for price, stock or order status. A hosted model would require appropriate customer-data controls.

## Validation and delivery

Run `python -m unittest discover -s tests -v`. For a real GPU evaluation, run `python scripts/evaluate_local.py --data-dir "$DATA_DIR" --model "$OLLAMA_MODEL"`. It prints the raw model answer, model-selected tools, prefetched policy sections, and checks for twelve scenarios. A failed case exits nonzero. The checks are a limited regression aid, not a complete proof of correctness; review the answers manually. GitHub Actions runs Python compilation, unit tests, and Docker build on pushes and pull requests.

See [examples.md](examples.md) for recorded model conversations and [CHECKLIST.md](CHECKLIST.md) for case and submission requirements.
