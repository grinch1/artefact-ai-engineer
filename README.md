# Empório da Música — AI customer service agent

A Python prototype for the Artefact AI Engineer case. A language model answers customers in Brazilian Portuguese using three read-only tools for instruments, orders, and the supplied policy PDF. There are no fixed customer-facing answers: every chat response is generated by the selected model. The application retrieves relevant manual sections before each model response, including when the model does not choose `get_policy` itself.

## Run on the private Mainframe

The case ZIP supplies six CSVs and an internal policy PDF. Keep them outside the repository. Set `DATA_DIR` to the extracted `data` directory, which must contain the `products`, `categories`, `promotions`, `orders`, and `customers` CSVs and one PDF. The `order_items` CSV is outside the current tool scope.

Install dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export DATA_DIR=/absolute/path/to/case/data
```

With authorized SSH access to `mainframe`, create a private local tunnel to Ollama in one terminal:

```bash
ssh -N -L 127.0.0.1:11435:127.0.0.1:11434 mainframe
```

In another terminal:

```bash
export AGENT_MODE=ollama
export OLLAMA_BASE_URL=http://127.0.0.1:11435/v1
export OLLAMA_MODEL=qwen3:14b
uvicorn api:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000/` for the web chat or `http://127.0.0.1:8000/docs` for the API. The interface needs the server; opening `web/index.html` as a `file://` page does not start a chat. For a CLI chat, use `python agent.py --data-dir "$DATA_DIR" --ollama`.

The Mainframe has two RTX 3090 GPUs. The tunnel is local only and does not publish Ollama. The separate `ager-agents-platform` repository documents a private OpenAI-compatible gateway for its own clients; this isolated experiment uses SSH forwarding rather than modifying that platform or claiming gateway integration.

## Hosted model option

Set `AGENT_MODE=openai` and `OPENAI_API_KEY` to use a hosted model through the Responses API. `OPENAI_MODEL` selects the model and currently defaults to `gpt-5.4-mini`; this path has not yet had an end-to-end model evaluation. API billing is separate from a ChatGPT Plus subscription. Do not place keys in the repository or Docker image. The CLI uses hosted mode when `--ollama` is omitted and an API key is configured. `--demo` only prints retrieval results; it does not produce chat responses.

Docker builds the same API with private data mounted read-only. A container needs network access to the chosen model endpoint; the local SSH tunnel address inside a container is not the host's loopback address. This runtime networking has not been verified locally.

```bash
docker build -t emporio-agent .
docker run --rm -p 8000:8000 -e AGENT_MODE=openai -e OPENAI_API_KEY \
  -v "$DATA_DIR:/data:ro" emporio-agent
```

## Architecture and decisions

`POST /chat` keeps a short conversation in memory. The small HTML/CSS/JavaScript interface calls the same endpoint. The model may call only `search_products`, `get_order`, and `get_policy`; it cannot generate arbitrary SQL or change source files. CSVs are loaded into typed in-memory SQLite tables at startup. Only active promotions are applied. `search_products` returns current and original prices, promotion percentage, PIX price, and stock from the snapshot. `get_order` returns a status only when the order number and purchase email match; it omits customer contact details.

The PDF is split into sections, ranked by a transparent keyword score, and returned with page and section numbers. Before **every** model answer, the application calls `get_policy` with the customer's question and passes up to three relevant excerpts to the model. The model may make additional tool calls. Retrieval is deterministic, but the customer-facing response is always model-generated. This keeps the evaluation honest: an incorrect interpretation remains visible as a failure, not replaced with a scripted answer. The small manual does not yet need an external vector database; section-level keyword retrieval can still miss paraphrases.

The policy prefetch is a grounding step, not a guarantee of compliance. In an initial Qwen 2.5 7B trial, the model invented accessory availability and misapplied installment minimums even after seeing the relevant section. Qwen3 14B is the selected local model because it handled those rules better in a like-for-like trial. Its wording still varies: one repeated answer rejected 10x correctly but misstated the value of a suggested 6x installment. We tightened the instruction to focus on the option asked, and the evaluator checks that observed failure pattern; manual review remains necessary. A paid hosted model remains a later option. No production readiness is claimed.

The PDF has inconsistent phone and email details across sections, so the agent is instructed not to volunteer them. The CSVs are static snapshots, not live inventory or carrier tracking. Sessions reset on restart. This prototype has no authentication or rate limiting and should not be exposed publicly. Matching a purchase email is a demonstration guard, not strong identity verification. A hosted model would require appropriate customer-data controls.

## Validation and delivery

Run `python -m unittest discover -s tests -v`. For a real GPU evaluation, run `python scripts/evaluate_local.py --data-dir "$DATA_DIR" --model "$OLLAMA_MODEL"`. It prints the raw model answer, model-selected tools, prefetched policy sections, and checks for nine scenarios. A failed case exits nonzero. The checks are a limited regression aid, not a complete proof of correctness; review the answers manually. GitHub Actions runs Python compilation, unit tests, and Docker build on pushes and pull requests.

See [examples.md](examples.md) for recorded model conversations and [CHECKLIST.md](CHECKLIST.md) for case and submission requirements.
